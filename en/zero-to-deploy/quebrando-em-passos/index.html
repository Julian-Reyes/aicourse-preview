From Zero to Deploy · Module 2 · Lesson 2.2

Breaking a project into steps

Why big requests go wrong, and how to split any app into small steps you can test.

⏱ 15 min

The problem with giant requests

“Build the whole app” almost always ends the same way: hundreds of lines at once, something broken in the middle, and no idea where. The bigger the request, the harder it is to find the mistake.

The fix is simple: small steps, each one testable.

The golden rule

Every step ends with something you can see working in the browser. If you can’t test it, the step is still too big (or too abstract).

One whole feature at a time

A common mistake is splitting by “layers”: all the HTML first, then all the CSS, then all the JavaScript. That way, nothing works until the very end.

The right way is to build one complete feature at a time: the add button, with its HTML, its styling, and its code. Tested, works? Next.

Put in order

The shopping list steps, in order

  1. 1An input and a button that add an item to the list
  2. 2A button to delete an item
  3. 3Save the list in the browser so it doesn't disappear on reload
  4. 4Publish on GitHub Pages
  5. 5Clicking an item marks it as bought (crossed out)
  6. 6A page with a title and a fixed sample list
  7. 7Adjust the look for phones

Good step or too big?

Sort it
  • Build the whole app
  • Add an input and a button that puts the text in the list
  • Build the server, the login, and the database
  • Save the list in the browser so it doesn't disappear on reload
  • Make everything look nice and professional
  • Show "No items yet" when the list is empty

Put the steps in the spec

Add a Steps section to your SPEC.md. If you don’t know where to start, ask Claude for help:

Read SPEC.md and propose a list of small steps to build the app. Each step should end with something I can test in the browser. Don't write code yet.

Review the list: cut anything too big, merge anything too small. Then work like this:

Build step 1 from SPEC.md and stop so I can test it.
💡
Save a version after each step

When a step works, save a version of the project (a “commit”, which you saw in the GitHub Pages lesson and go deeper on in module 6). If the next step goes wrong, you can return to the last good version in seconds.
